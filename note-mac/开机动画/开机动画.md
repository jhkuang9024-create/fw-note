# 开机动画源码分析

## 1. 模块定位

`bootanimation` 是 Android 在系统早期启动阶段用于显示开机内容的原生服务。它的职责不是普通应用层动画展示，而是在桌面和 SystemUI 等上层界面尚未完全起来之前，直接通过 `SurfaceFlinger + EGL/OpenGL` 把开机动画、关机动画，或者厂商扩展的开机视频显示到屏幕上。

从当前目录源码看，这个模块包含两类能力：

1. 标准 `bootanimation.zip` 帧动画播放。
2. 厂商定制的 `boot video` 视频播放能力。

同时它还支持：

1. part 音频播放。
2. 开机进度展示。
3. 时钟显示。
4. 动态换色。
5. 多屏显示。
6. 按键调节开机视频音量。

---

## 3. 服务启动方式

`bootanim.rc` 中定义了服务：

```rc
service bootanim /system/bin/bootanimation
    class core animation
    user graphics
    group graphics audio input
    disabled
    oneshot
    ioprio rt 0
    task_profiles MaxPerformance
```

这里可以看出几个关键点：

1. 进程名就是 `/system/bin/bootanimation`。
2. 属于 `core animation` 类服务。
3. 运行用户是 `graphics`，组里还有 `audio`、`input`，说明它不只是画图，还要访问音频和输入设备。
4. `oneshot` 表示它不是常驻守护进程，而是一次性服务。
5. `disabled` 表示不会在 init 解析 rc 时立刻启动，而是在系统特定阶段由外部触发。

所以业务上可以理解为：

系统进入开机动画阶段时，`init` 拉起 `bootanimation`，等系统启动完成后，再通过属性通知它退出。

## 4. 主入口流程

主入口在 `bootanimation_main.cpp`：

```cpp
int main()
{
    setpriority(PRIO_PROCESS, 0, ANDROID_PRIORITY_DISPLAY);

    bool noBootAnimation = bootAnimationDisabled();
    if (!noBootAnimation) {
        sp<ProcessState> proc(ProcessState::self());
        ProcessState::self()->startThreadPool();

        sp<BootAnimation> boot = new BootAnimation(audioplay::createAnimationCallbacks());

        waitForSurfaceFlinger();

        boot->run("BootAnimation", PRIORITY_DISPLAY);

        IPCThreadState::self()->joinThreadPool();
    }
    return 0;
}
```

它的处理逻辑非常清晰：

1. 把自身优先级调高到显示级别，保证开机阶段渲染线程优先运行。
2. 调用 `bootAnimationDisabled()` 判断当前是否需要跳过开机动画。
3. 初始化 Binder 线程池。
4. 创建 `BootAnimation` 对象，并注入音频播放回调。
5. 等待 `SurfaceFlinger` 服务起来。
6. 启动 `BootAnimation` 线程。
7. 主线程进入 Binder 线程池等待。

这里的重点是：

- `bootanimation` 不是直接在 `main()` 里画图，而是把核心逻辑放在 `BootAnimation` 线程里。
- 它依赖 `SurfaceFlinger`，因为最终显示 Surface 需要由 `SurfaceFlinger` 管理。

## 5. 是否禁用开机动画

`BootAnimationUtil.cpp` 中的 `bootAnimationDisabled()` 负责判断当前是否直接跳过：

### 5.1 厂商 bootvideo 特殊逻辑

```cpp
int type = property_get_int32("persist.vendor.media.bootvideo", 0);
type /= 1000;
if (type == 3 && property_get_int32("persist.vendor.media.bootvideo.tsplayer", 0) > 0) {
    return true;
}
```

说明这个版本里，厂商把 `persist.vendor.media.bootvideo` 的千位以上作为模式位使用。

当：

1. `type == 3`
2. `persist.vendor.media.bootvideo.tsplayer > 0`

时，直接禁用传统 bootanimation，说明平台可能完全改为其他视频链路。

### 5.2 调试属性禁用

```cpp
property_get("debug.sf.nobootanimation", value, "0");
if (atoi(value) > 0) {
    return true;
}
```

这是 Android 常见调试开关。

### 5.3 静默开机场景

```cpp
property_get("ro.boot.quiescent", value, "0");
if (atoi(value) > 0) {
    if (!property_get_bool("ro.bootanim.quiescent.enabled", false)) {
        return true;
    }
}
```

说明设备在某些静默启动模式下，也可以不显示开机动画。

## 6. 等待 SurfaceFlinger

`waitForSurfaceFlinger()` 会轮询查询 `SurfaceFlinger` 服务：

```cpp
while (sm->checkService(name) == nullptr) {
    usleep(100ms);
}
```

原因很直接：

开机动画最终要创建 Surface 并提交到显示系统，如果 `SurfaceFlinger` 还没起来，后续所有图形初始化都无法完成。

所以从业务上讲：

`bootanimation` 是一个依赖显示服务的早期 UI 进程，它本身不能脱离 `SurfaceFlinger` 独立工作。

## 7. BootAnimation 类整体职责

`BootAnimation` 定义在 `BootAnimation.h`，继承自：

1. `Thread`
2. `IBinder::DeathRecipient`

这意味着它具备两种能力：

1. 自己作为线程执行动画主循环。
2. 监听 `SurfaceFlinger` 死亡事件，若显示服务挂掉则主动退出。

### 7.1 主要成员

可以从头文件中把它理解为几个子模块：

#### 1. 渲染相关

- `mSession`
- `mDisplay`
- `mContext`
- `mSurface`
- `mFlingerSurfaceControl`
- `mFlingerSurface`
- `mWidth`
- `mHeight`

用于建立 Surface、EGL 和 OpenGL 渲染环境。

#### 2. 动画资源相关

- `mZipFileName`
- `mAnimation`
- `mLoadedFiles`

用于定位和加载 `bootanimation.zip`。

#### 3. 扩展显示能力

- `mClockEnabled`
- `mTimeIsAccurate`
- `mTimeCheckThread`
- `mDisplayEventReceiver`
- `mLooper`

用于时钟显示、时间校准检测、显示事件监听。

#### 4. 厂商视频能力

- `mMediaPlayer`
- `mInputReaderThread`
- `mVol`
- `mMute`
- `mConfig`

用于 boot video、音量控制和输入事件处理。

#### 5. 回调机制

- `mCallbacks`

用于把动画播放和音频播放解耦。

## 8. BootAnimation 生命周期

### 8.1 构造函数

构造函数里主要做了几件事：

1. 创建 `SurfaceComposerClient`。
2. 读取 `sys.powerctl` 判断当前是开机还是关机动画。
3. 读取旋转相关属性：
   - `persist.sys.builtinrotation`
   - `persist.vendor.hwc.primary`
4. 记录启动时序日志。

因此构造阶段的业务重点不是“开始画图”，而是确定运行上下文：

1. 当前是 boot 还是 shutdown。
2. 屏幕物理方向和逻辑方向是什么。

### 8.2 `onFirstRef()`

`onFirstRef()` 中做了一个很关键的动作：

```cpp
preloadAnimation();
```

这一步会在真正等待 `SurfaceFlinger` 完全就绪前，提前尝试加载动画包内容，减少后面开播的启动时延。

从日志注释也能看出，作者就是为了“把可能较慢的 zip 读取前置”。

### 8.3 `readyToRun()`

这是线程启动前最核心的初始化函数，主要完成：

1. 加载默认资源。
2. 获取物理显示器 ID。
3. 读取显示分辨率和活动显示模式。
4. 创建 `SurfaceControl` 和 `Surface`。
5. 初始化 EGLDisplay、EGLSurface、EGLContext。
6. 设置显示投影和旋转。
7. 初始化多屏镜像显示。
8. 注册 `DisplayEventReceiver`。

可以把它理解为：

`readyToRun()` 负责搭出“能把图画到屏幕上”的基础设施。

### 8.4 `threadLoop()`

`threadLoop()` 是真正的业务分发入口，它决定本次到底播什么：

1. 没有 zip 动画文件时，播放默认 Android logo 动画。
2. 有 zip 时，根据厂商配置决定播放：
   - 仅 bootanimation
   - 先 bootanimation 后 bootvideo
   - 先 bootvideo 后 bootanimation
   - 仅 bootvideo

这部分是整个模块的总控逻辑。

## 9. 动画资源查找逻辑

### 9.1 查找函数

动画文件查找在：

- `findBootAnimationFile()`
- `findBootAnimationFileInternal()`

### 9.2 开机资源优先级

标准开机动画查找顺序：

1. `/apex/com.android.bootanimation/etc/bootanimation.zip`
2. `/product/media/bootanimation-dark.zip` 或 `/product/media/bootanimation.zip`
3. `/oem/media/bootanimation.zip`
4. `/system/media/bootanimation.zip`

其中 `ro.boot.theme == 1` 时优先取 dark 版本。

### 9.3 关机与 userspace reboot

还支持：

1. `shutdownanimation.zip`
2. `userspace-reboot.zip`

这说明当前实现不仅处理开机，也处理关机和用户态重启展示。

### 9.4 选择方式

`findBootAnimationFileInternal()` 的逻辑很简单：

按顺序遍历路径，只要 `access(path, R_OK) == 0` 就选中该文件。

所以这里是典型的“多路径兜底 + 优先级覆盖”设计。

## 10. 动画描述结构

头文件里的数据结构非常关键。

### 10.1 `Animation`

表示整个动画包，主要包含：

- `fps`
- `width`
- `height`
- `progressEnabled`
- `parts`
- `zip`
- `clockFont`
- `progressFont`
- `dynamicColoringEnabled`

### 10.2 `Part`

表示 `desc.txt` 中的一段动画，主要字段有：

- `count`：循环次数，`0` 表示无限循环。
- `pause`：该 part 结束后额外停顿多少帧。
- `clockPosX/clockPosY`：时钟位置。
- `path`：对应 zip 中的目录名。
- `frames`：这个目录下的所有帧。
- `playUntilComplete`：是否必须播完整。
- `framesToFadeCount`：退出时的淡出帧数。
- `backgroundColor`：背景色。
- `audioData/audioLength`：该 part 附带的 wav 音频。
- `useDynamicColoring`：是否使用动态着色。
- `postDynamicColoring`：是否属于动态着色之后的 part。

### 10.3 `Frame`

表示一张 PNG 帧，包含：

- `name`
- `map`
- `trimX`
- `trimY`
- `trimWidth`
- `trimHeight`
- `tid`

这里的 `trim*` 信息是为了支持裁剪帧，从而节省内存和纹理开销。

---

## 11. `bootanimation.zip` 格式与业务含义

`FORMAT.md` 说明了 zip 包结构：

```text
desc.txt
part0/
part1/
...
partN/
```

### 11.1 `desc.txt` 首行

```text
WIDTH HEIGHT FPS [PROGRESS]
```

用于定义整套动画的：

1. 分辨率
2. 帧率
3. 是否显示 progress

### 11.2 part 行格式

```text
TYPE COUNT PAUSE PATH [FADE [#RGBHEX [CLOCK1 [CLOCK2]]]]
```

#### `TYPE` 的含义

- `p`：普通 part，可被中断。
- `c`：完整播放 part，即使系统准备退出也要播完。
- `f`：可中断且支持淡出。

这是业务上非常重要的一点：

开机动画不是所有段都同等对待，某些 part 可以在系统 boot 完成后立即跳出，某些 part 则要求完整展示。

### 11.3 支持的附加资源

每个 part 目录中除了 PNG 帧之外，还可包含：

1. `trim.txt`
2. `audio.wav`

#### `trim.txt`

每一行对应一帧，格式如：

```text
713x165+388+914
```

表示该帧原图经过裁剪后在动画画布中的位置和尺寸。

#### `audio.wav`

表示该 part 播放开始时可以伴随一段声音。

---

## 12. `desc.txt` 解析逻辑

解析入口是 `parseAnimationDesc(Animation&)`。

### 12.1 解析首行

它先解析首行得到：

- `animation.width`
- `animation.height`
- `animation.fps`
- `animation.progressEnabled`

### 12.2 动态着色行

如果匹配到：

```text
dynamic_colors PATH #RGBHEX0 #RGBHEX1 #RGBHEX2 #RGBHEX3 ...
```

则开启动态着色，并保存：

1. 哪个 part 是动态着色 part。
2. 四组起始颜色。
3. 颜色过渡的起止帧区间。

### 12.3 普通 part 行

解析普通行后会构造 `Animation::Part`，并设置：

1. `playUntilComplete`
2. `framesToFadeCount`
3. `count`
4. `pause`
5. `path`
6. `backgroundColor`
7. `clockPosX/Y`
8. 动态颜色属性

### 12.4 `$SYSTEM`

源码还支持一个特殊行：

```text
$SYSTEM
```

这表示当前动画包中可以嵌套引用系统默认 bootanimation。

它的实现方式是：

直接调用 `loadAnimation(SYSTEM_BOOTANIMATION_FILE)` 把系统动画再作为一个 part 挂进去。

---

## 13. zip 预加载逻辑

预加载入口是 `preloadZip(Animation&)`。

这个函数会遍历 zip 中所有 entry，然后按类型分发：

### 13.1 字体文件

如果是：

- `clock_font.png`
- `progress_font.png`

就挂到 `animation.clockFont` / `animation.progressFont`。

### 13.2 音频文件

如果是 `audio.wav`，则挂到对应 part 的：

- `audioData`
- `audioLength`

### 13.3 trim 信息

如果是 `trim.txt`，就存到对应 part 的 `trimData`。

### 13.4 普通 PNG 帧

则生成 `Animation::Frame`，默认：

- `trimWidth = animation.width`
- `trimHeight = animation.height`
- `trimX = 0`
- `trimY = 0`

后续如果存在 `trim.txt`，再覆盖这些值。

### 13.5 trim 二次修正

遍历完 zip 后，还会再次处理 `trimData`，逐帧解析 `WxH+X+Y` 格式，把每帧的裁剪坐标设置进去。

这一步的意义是：

zip 中帧图本身可能只是局部图块，但渲染时仍然需要知道它在完整动画画布中的真实位置。

---

## 14. OpenGL / EGL 初始化逻辑

图形系统初始化主要在 `readyToRun()` 中完成。

### 14.1 获取显示信息

它会先通过 `SurfaceComposerClient::getPhysicalDisplayIds()` 获取物理显示器列表，再取活动显示模式 `DisplayMode`。

### 14.2 创建 SurfaceControl

```cpp
sp<SurfaceControl> control = session()->createSurface(
    String8("BootAnimation"),
    resolution.getWidth(),
    resolution.getHeight(),
    PIXEL_FORMAT_RGBA_8888,
    ISurfaceComposerClient::eOpaque);
```

也就是说，开机动画本质上也是一个系统层 Surface。

### 14.3 创建 EGL 环境

接着依次完成：

1. `eglGetDisplay`
2. `eglInitialize`
3. `eglCreateWindowSurface`
4. `eglCreateContext`
5. `eglMakeCurrent`

至此，bootanimation 拿到了一个可用的 OpenGL ES 2.0 渲染上下文。

### 14.4 旋转与投影

它还会结合以下信息处理显示方向：

1. `persist.sys.builtinrotation`
2. `persist.vendor.hwc.primary`
3. `ro.bootanim.set_orientation_<displayId>`

这说明 bootanimation 的显示方向不完全依赖默认屏幕方向，而是可以通过属性做启动阶段单独控制。

---

## 15. Shader 初始化逻辑

`initShaders()` 初始化了两类 shader：

1. 图像 shader
2. 文本 shader

其中图像 shader 又分两种：

1. 普通图片渲染 shader
2. 动态颜色渲染 shader

### 15.1 普通图像 shader

普通模式下，片元 shader 逻辑基本就是：

1. 采样纹理颜色。
2. 乘上透明度。
3. 根据 `uFade` 控制淡出。

### 15.2 动态颜色 shader

动态着色模式下，PNG 的 `RGBA` 四个通道不再只是单纯颜色值，而是被当作四个区域 mask：

1. R 通道映射 color0
2. G 通道映射 color1
3. B 通道映射 color2
4. A 通道映射 color3

最终颜色会按 `uColorProgress` 在起始色和结束色之间插值。

也就是说：

这个特性不是“替换整张图”，而是“把图当成颜色权重模板来着色”。

---

## 16. `threadLoop()` 总控逻辑

`threadLoop()` 是业务调度中心。

### 16.1 无动画包时

如果 `mZipFileName` 为空：

```cpp
result = android();
```

即播放默认 Android logo 动画。

### 16.2 有动画包时

若存在 zip，则继续看 `persist.vendor.media.bootvideo`。

源码把该属性拆分为：

1. 千位以上：模式位 `mConfig`
2. 个位到百位：音量值 `mVol`

#### 模式定义

- `CONFIG_BOOTANIM = 0`：只播 bootanimation
- `CONFIG_BOOTANIM_BOOTVIDEO = 1`：先动画后视频
- `CONFIG_BOOTVIDEO_BOOTANIM = 2`：先视频后动画
- `CONFIG_BOOTVIDEO = 3`：只播视频

这就是当前项目相对 AOSP 最重要的厂商扩展点之一。

### 16.3 退出收尾

无论哪条路径，最后都会做：

1. 设置 `service.bootvideo.exit = 0`
2. 调用 `mCallbacks->shutdown()`
3. 销毁 EGLContext / EGLSurface
4. 清理 Surface
5. `IPCThreadState::self()->stopProcess()`

说明这个线程会完整负责自身图形资源释放。

---

## 17. 默认 Android logo 动画

当找不到任何 zip 动画资源时，会退回 `android()`。

它会加载默认资源：

- `images/android-logo-mask.png`
- `images/android-logo-shine.png`

然后通过简单的平移和叠加，形成 Android logo 上的光效滑动动画。

这个逻辑是纯 OpenGL 绘制，没有 zip、part、frame 的概念。

所以 `android()` 可以视为最基础的兜底方案。

## 18. 标准 zip 动画播放总流程

zip 动画主流程在 `movie()` 中。

### 18.1 关键步骤

`movie()` 做的事情可以概括为：

1. 若动画未加载，则调用 `loadAnimation()`。
2. 初始化音频回调。
3. 判断是否存在可显示时钟的 part。
4. 检测设备是否允许显示时钟。
5. 检查是否支持 NPOT 纹理。
6. 初始化字体纹理。
7. 必要时启动时间检测线程。
8. 如果启用了动态颜色，则加载动态颜色属性。
9. 调用 `playAnimation(*mAnimation)` 逐 part、逐帧播放。
10. 播放结束后释放字体和动画资源。

### 18.2 时钟是否显示

时钟显示不是无条件开启，需要满足：

1. 至少一个 part 配置了合法时钟坐标。
2. `persist.sys.bootanim.clock.enabled == true`
3. 当前系统时间被判断为准确。

否则不会显示时间。

---

## 19. 时间准确性检测

时间相关逻辑主要在：

- `updateIsTimeAccurate()`
- `TimeCheckThread`

### 19.1 为什么需要单独判断时间是否准确

开机早期系统时间往往还没同步好，如果直接显示时钟，可能会显示错误时间。

所以源码会先检查：

1. `/data/bootanim/time/time_is_accurate`
2. `/data/bootanim/time/last_time_change`
3. `/data/bootanim/time/time_format_12_hour`

### 19.2 判断逻辑

如果存在 `time_is_accurate` 文件，直接认为时间可信。

否则会读取 `last_time_change`，并结合当前 `CLOCK_REALTIME` 判断最近一次改时是否落在合理范围内。

### 19.3 监听机制

如果时间暂时不准，但又允许显示时钟，则拉起 `TimeCheckThread`：

1. 用 `inotify` 监听 `/data/bootanim`。
2. 如果 `time` 目录出现，再继续监听 `/data/bootanim/time`。
3. 当 `last_time_change` 或 `time_is_accurate` 更新时，重新判断时间准确性。

这样做的好处是：

开机动画在播放过程中，如果系统时间同步完成，可以动态开始显示正确时钟，而不是等下次开机。

## 20. `playAnimation()` 逐帧播放细节

`playAnimation()` 是整个 zip 动画的核心循环。

### 20.1 循环层级

它的嵌套关系是：

1. 外层遍历 `parts`
2. 中层处理每个 part 的循环次数 `count`
3. 内层逐帧遍历 `frames`

### 20.2 part 嵌套

如果某个 `part.animation != nullptr`，说明它引用了一个嵌套动画包，例如 `$SYSTEM`，此时会递归调用 `playAnimation()`。

### 20.3 part 播放前回调

在每个 part 开始前会调用：

```cpp
mCallbacks->playPart(i, part, r);
```

这就是音频播放切入点。

### 20.4 单帧渲染流程

每一帧大致执行：

1. 处理显示事件 `processDisplayEvents()`
2. 计算缩放比例 `ratio_w / ratio_h`
3. 计算动画在屏幕中的居中位置
4. 如果纹理尚未生成，则用 `initTexture()` 解码 PNG
5. 结合 `trimX/Y/Width/Height` 计算绘制区域
6. 清屏
7. 使用 image shader 绘制当前纹理
8. 若允许则叠加时钟
9. 若允许则叠加启动进度
10. 调整 viewport 裁剪效果
11. `eglSwapBuffers()` 提交到屏幕
12. 按帧率 sleep

### 20.5 淡出逻辑

当收到退出请求且当前 part 支持淡出时：

```cpp
fade = ++fadedFramesCount / part.framesToFadeCount;
```

这个 `fade` 会传入 shader 中，逐步把 alpha 降下来。

### 20.6 进度显示

如果动画启用了 `progressEnabled`，并且当前 part 是最后一个 part，则会读取：

- `service.bootanim.progress`

把它绘制成百分比文字。

## 21. 退出机制

退出属性是：

- `service.bootanim.exit`

在 `checkExit()` 中每轮检查：

```cpp
property_get(EXIT_PROP_NAME, value, "0");
if (atoi(value)) {
    requestExit();
}
```

### 21.1 各类 part 的退出行为

#### `p` 类型

可中断，适合循环等待系统完成启动的动画段。

#### `c` 类型

必须播完，即使系统已经 boot 完成也不会立刻停。

#### `f` 类型

收到退出请求后，会进入淡出阶段再结束。

所以从业务层理解：

`service.bootanim.exit` 不是“强杀动画”，而是“通知动画按规则优雅退出”。

## 22. 音频播放逻辑

音频实现位于 `audioplay.cpp`。

### 22.1 整体设计

它没有直接写死在 `BootAnimation` 主循环里，而是通过回调机制接入：

1. `main()` 创建 `BootAnimation` 时注入 `audioplay::createAnimationCallbacks()`
2. `BootAnimation` 播放每个 part 前调用 `Callbacks::playPart()`
3. 音频模块据此决定是否播放对应 part 的 `audio.wav`

### 22.2 音频引擎初始化

`AudioAnimationCallbacks::init()` 会扫描所有 part，找到第一个带音频的 part，然后启动 `InitAudioThread`：

1. 创建 OpenSL ES 引擎
2. 创建 OutputMix
3. 创建 BufferQueue AudioPlayer

### 22.3 为什么只拿第一个音频初始化

源码默认假设所有 part 的音频格式一致，因此只拿第一段 `audio.wav` 作为示例格式去初始化 player。

### 22.4 实际播放时机

`playPart()` 中只有在以下条件满足时才播：

1. `playNumber == 0`，即 part 第一次播放。
2. 当前 part 存在 `audioData`。
3. `playSoundsAllowed()` 返回 true。

### 22.5 哪些情况下不允许播放声音

`playSoundsAllowed()` 会拦截：

1. `sys.boot_completed == true`，说明不是冷启动。
2. `sys.powerctl` 非空，说明正在关机。
3. `persist.sys.bootanim.play_sound == false`
4. `ro.boot.bootreason` 属于黑名单：
   - `kernel_panic`
   - `Panic`
   - `Watchdog`

说明系统在异常重启场景下不想播放开机提示音。

## 23. 厂商 boot video 扩展

这一部分是当前源码相对标准 AOSP 最大的差异点。

### 23.1 相关属性和文件

源码里定义了：

- `persist.sys.bootvideo`
- `persist.vendor.media.bootvideo`
- `service.bootvideo.exit`
- `/data/bootvideo`
- `/vendor/etc/bootvideo`
- `/system/media/bootvideo.zip`
- `/vendor/etc/bootvideo.zip`

其中：

1. 视频文件来自 `/data/bootvideo` 或 `/vendor/etc/bootvideo`
2. 音量 UI 动画来自 `bootvideo.zip`

### 23.2 配置模式

`persist.vendor.media.bootvideo` 被拆分使用：

#### 高位

`/ 1000` 后得到模式：

- `0`：只播放 bootanimation
- `1`：先 bootanimation 后 bootvideo
- `2`：先 bootvideo 后 bootanimation
- `3`：只播放 bootvideo

#### 低位

`% 1000` 后得到音量值。

这意味着一个属性同时编码了“播放策略 + 默认音量”。

## 24. `bootVideo()` 视频播放流程

`bootVideo()` 是视频模式的主逻辑。

### 24.1 查找视频文件

按顺序查找：

1. `/data/bootvideo`
2. `/vendor/etc/bootvideo`

找到第一个可读文件后作为当前视频资源。

### 24.2 创建视频显示 Surface

它会额外创建一个名为 `BootVideo` 的 Surface：

```cpp
createSurface(String8("BootVideo"), ..., PIXEL_FORMAT_RGB_565)
```

然后把该 Surface reparent 到 bootanimation 的主 SurfaceControl 下。

说明这里的视频显示不是单独进程窗口，而是 bootanimation 进程自己创建的子显示层。

### 24.3 等待媒体服务

播放前会先轮询等待 `media.player` 服务启动。

因为 boot video 依赖 `MediaPlayerService`，而它在开机早期不一定已经可用。

### 24.4 MediaPlayer 初始化

主要步骤：

1. 打开本地视频文件 fd
2. `mMediaPlayer = new MediaPlayer()`
3. 绑定监听器 `BootVideoListener`
4. `setDataSource(fd, ...)`
5. `setVideoSurfaceTexture(new_st)`
6. 设置音频流类型为 `AUDIO_STREAM_SYSTEM`
7. `prepare()`
8. `start()`

### 24.5 视频尺寸变化监听

`BootVideoListener::notify()` 会处理：

1. `MEDIA_SET_VIDEO_SIZE`
2. `MEDIA_PLAYBACK_COMPLETE`
3. `MEDIA_ERROR`

其中播放完成或错误都会把：

- `isPlayCompleted = true`

作为结束标志。

## 25. 开机视频音量控制

boot video 模式下还有一个很典型的厂商扩展：

开机阶段允许用户按实体键调节视频音量。

### 25.1 输入线程

`InputReaderThread` 专门负责监听 `/dev/input`：

1. `readyToRun()` 中通过 `inotify` 监听输入设备目录变化。
2. `scan_dir()` 打开现有输入设备。
3. `doThreadLoop()` 中用 `poll()` 持续监听所有输入 fd。

### 25.2 支持的按键

源码识别：

- `KEY_VOLUMEUP`
- `KEY_VOLUMEDOWN`
- `KEY_PAGEUP`
- `KEY_PAGEDOWN`
- `KEY_MUTE`

最后调用：

- `bootVideoSetVolume(UP)`
- `bootVideoSetVolume(DOWN)`
- `bootVideoSetVolume(MUTE)`

### 25.3 音量状态维护

`bootVideoSetVolume()` 的逻辑是：

1. 修改 `mVol` 或 `mMute`
2. 调用 `mMediaPlayer->setVolume(vol, vol)`
3. 同步属性 `persist.sys.bootvideo`

这说明：

当前音量不是只在内存里改，而是持久化到系统属性中，下次开机仍可沿用。

## 26. 开机视频音量 UI

`bootVideoVolumeUI()` 会加载：

- `/system/media/bootvideo.zip`
- `/vendor/etc/bootvideo.zip`

把它作为一个普通 animation zip 解析，然后只用其中第一段 part 的帧作为音量 UI 素材。

### 26.1 显示方式

它本质上不是单独界面系统，而是：

1. 根据当前 `mVol` 选择对应帧
2. 将该帧作为纹理绘制到屏幕上
3. 通过调整 `SurfaceControl` layer 决定显示或隐藏

### 26.2 自动隐藏

当用户调节过音量后，会记录 `hideVolUIStartTime`。

若超过 `HIDE_VOL_UI_WAIT_SLEEP_MS = 4000ms` 且当前非静音，则自动隐藏音量 UI。

所以这个 UI 的业务行为是：

1. 按键后立即显示。
2. 4 秒无操作自动消失。

## 27. 多屏与显示事件处理

`readyToRun()` 里支持多显示器。

### 27.1 指定显示器属性

可以通过：

- `persist.service.bootanim.displays`

指定在哪些物理显示器上展示开机动画。

### 27.2 默认多屏策略

若未显式指定，但系统存在多个物理显示器，源码会给其他显示器做 layer stack 或镜像相关设置。

说明该实现并不只考虑单屏手机场景，也考虑了盒子或多屏设备。

### 27.3 显示事件

`DisplayEventReceiver + Looper` 用于在每帧前 `pollOnce(0)` 处理显示事件。

这可以让 bootanimation 在显示模式切换、分辨率变化、显示裁剪调整时及时响应。

## 28. viewport 裁剪动画

`handleViewport()` 处理一个较细节但很有用的效果：

它读取：

- `persist.sys.displayinset.top`

并在 boot 结束前做顶部 inset 的过渡裁剪。

简单理解：

有些设备最终显示区域和开机阶段显示区域并不完全一致，bootanimation 会在结束前做一次平滑裁剪/位移动画，避免从开机画面切到正式系统界面时出现突兀跳变。

## 31. 从业务角度如何理解这份源码

如果不从代码细节，而从业务设计看，这套开机动画实现可以概括为：

### 31.1 它是一个“启动阶段展示框架”

不是单纯播放几张 PNG，而是一个完整框架，统一处理：

1. 资源查找
2. 资源解析
3. 图形渲染
4. 动画播放调度
5. 音频播放
6. 视频播放
7. 输入监听
8. 多屏适配
9. 时间与进度叠加
10. 系统启动完成后的优雅退出

### 31.2 它的退出不是暴力停止，而是按 part 规则退出

这保证了开机动画在系统启动完成的瞬间不会突然消失，而是能根据设计要求：

1. 立即结束
2. 播完整段
3. 淡出结束

### 31.3 它保留了 AOSP 标准能力，同时叠加了厂商视频方案

当前这份源码既保留了 Android 标准的 `bootanimation.zip` 能力，又加入了：

1. `bootvideo` 模式
2. 实体按键音量控制
3. bootvideo 音量 UI

这说明项目所在平台对启动展示效果有更强定制需求。

## 33. 总结

这套 `bootanimation` 源码可以总结为一句话：

它是 Android 开机阶段的底层展示引擎，标准能力负责播放 `bootanimation.zip` 帧动画，厂商扩展能力负责播放 boot video，并在整个过程中处理声音、时间、进度、输入、多屏和优雅退出等完整业务逻辑。

如果再浓缩一点，可以理解成下面这条主线：

```text
启动服务
  -> 选择动画或视频资源
  -> 创建显示 Surface 和 EGL 环境
  -> 解析 zip / 初始化视频播放器
  -> 逐帧渲染或播放视频
  -> 响应音频、时钟、进度、输入事件
  -> 等待系统启动完成信号
  -> 按规则退出并释放资源
```

这就是当前目录 `bootanimation` 的完整业务含义和详细处理逻辑。

## 34. 主流程时序图版梳理

这一节把前面的源码逻辑，按“时序图视角”再串一次，方便从系统启动全过程理解每个模块的职责边界。

### 34.1 整体开机主流程

```text
init
  -> 拉起 service bootanim
      -> /system/bin/bootanimation
          -> main()
              -> setpriority(PRIORITY_DISPLAY)
              -> bootAnimationDisabled()
              -> ProcessState::startThreadPool()
              -> new BootAnimation(callbacks)
                  -> 构造函数读取关机/旋转上下文
              -> waitForSurfaceFlinger()
              -> boot->run()
                  -> onFirstRef()
                      -> preloadAnimation()
                          -> findBootAnimationFile()
                          -> loadAnimation()
                              -> parseAnimationDesc()
                              -> preloadZip()
                  -> readyToRun()
                      -> 创建 SurfaceControl / Surface
                      -> 初始化 EGLDisplay / EGLContext / EGLSurface
                      -> 设置显示投影、旋转、多屏
                  -> threadLoop()
                      -> 根据属性决定播放模式
                      -> movie() 或 android() 或 bootVideo()
              -> joinThreadPool()
```

这个时序说明两件事：

1. `onFirstRef()` 先做资源预加载。
2. `readyToRun()` 再做图形环境初始化。

也就是说，源码把“资源准备”和“显示准备”刻意拆开了。

### 34.2 标准 zip 动画时序

```text
threadLoop()
  -> 判断 mZipFileName 是否为空
  -> 若存在 zip
      -> movie()
          -> 如 mAnimation 为空则 loadAnimation()
          -> mCallbacks->init(parts)
              -> 音频模块预初始化
          -> 检查时钟开关与时间准确性
          -> initFont(clock/progress)
          -> initDynamicColors()
          -> playAnimation(animation)
              -> for each part
                  -> playPart callback
                  -> for each frame
                      -> processDisplayEvents()
                      -> initTexture(PNG -> GL texture)
                      -> drawTexturedQuad()
                      -> drawClock()/drawProgress()
                      -> handleViewport()
                      -> eglSwapBuffers()
                      -> checkExit()
          -> 释放字体与动画资源
```

从这个链路看，`movie()` 更像“播放控制器”，而真正逐帧干活的是 `playAnimation()`。

### 34.3 zip 动画解析时序

```text
preloadAnimation()
  -> findBootAnimationFile()
      -> 按优先级查找 bootanimation/shutdown/userspace-reboot zip
  -> loadAnimation(zipPath)
      -> ZipFileRO::open()
      -> parseAnimationDesc()
          -> 解析 WIDTH HEIGHT FPS
          -> 解析 dynamic_colors
          -> 解析每个 part
          -> 解析 $SYSTEM
      -> preloadZip()
          -> 遍历 zip entry
          -> 识别 clock_font.png / progress_font.png
          -> 识别 audio.wav
          -> 识别 trim.txt
          -> 收集各 part 下的 PNG 帧
          -> 二次解析 trimData 到每一帧
```

这个链路的重点在于：

1. `desc.txt` 决定“如何播”。
2. zip 目录内容决定“播什么”。

### 34.4 音频播放时序

```text
main()
  -> new BootAnimation(audioplay::createAnimationCallbacks())

movie()
  -> mCallbacks->init(parts)
      -> AudioAnimationCallbacks::init()
          -> 找到首个带 audio.wav 的 part
          -> InitAudioThread::run()
              -> audioplay::create()
                  -> createEngine()
                  -> createBufferQueueAudioPlayer()

playAnimation()
  -> part 开始前 mCallbacks->playPart(i, part, r)
      -> AudioAnimationCallbacks::playPart()
          -> playSoundsAllowed()
          -> initAudioThread->join()
          -> audioplay::playClip(audioData)
```

可以看到，音频初始化被前置到了动画播放前，避免真正进入 part 时再临时建音频引擎造成卡顿。

### 34.5 时钟与时间检测时序

```text
movie()
  -> 检查是否有 part 配置时钟坐标
  -> 检查 persist.sys.bootanim.clock.enabled
  -> updateIsTimeAccurate()
      -> 检查 /data/bootanim/time/time_is_accurate
      -> 检查 /data/bootanim/time/last_time_change
  -> 若时间暂不准确
      -> TimeCheckThread::run()
          -> inotify 监听 /data/bootanim 和 /data/bootanim/time
          -> 文件变化后再次 updateIsTimeAccurate()

playAnimation()
  -> 每帧判断 mClockEnabled && mTimeIsAccurate
      -> drawClock()
```

这里的设计思路是：

系统时间一开始不准没关系，动画先播；一旦时间同步完成，后续帧就可以把时钟叠上去。

### 34.6 开机完成退出时序

```text
system_server / init 侧
  -> 设置 service.bootanim.exit = 1

BootAnimation 播放线程
  -> checkExit()
      -> requestExit()
  -> shouldStopPlayingPart()
      -> 根据 part 类型决定：
          p: 可中断
          c: 播完整段
          f: 淡出后退出
  -> 播放结束
      -> mCallbacks->shutdown()
      -> 销毁 EGLContext / EGLSurface
      -> 清理 Surface 与动画资源
```

这个流程说明 `service.bootanim.exit` 只是退出信号，不代表立即停止画面。

### 34.7 boot video 模式时序

```text
threadLoop()
  -> 读取 persist.vendor.media.bootvideo
  -> 解析 mConfig / mVol / mMute
  -> 根据模式选择：
      CONFIG_BOOTANIM
      CONFIG_BOOTANIM_BOOTVIDEO
      CONFIG_BOOTVIDEO_BOOTANIM
      CONFIG_BOOTVIDEO

若进入 bootVideo()
  -> 查找 /data/bootvideo 或 /vendor/etc/bootvideo
  -> 创建 BootVideo Surface
  -> waitForMediaPlayerService()
  -> MediaPlayer setDataSource / setSurface / prepare / start
  -> 启动 InputReaderThread
  -> bootVideoVolumeUI(listener)
  -> 等待 MEDIA_PLAYBACK_COMPLETE 或 MEDIA_ERROR
  -> 停止输入线程
  -> reset/stop MediaPlayer
  -> 某些模式下继续 movie()
```

这个链路说明 boot video 不是替换掉整个 `bootanimation` 进程，而是作为同一进程中的另一条播放分支。

### 34.8 开机视频音量控制时序

```text
bootVideo()
  -> InputReaderThread::run()
      -> 监听 /dev/input
      -> poll 所有输入设备
      -> 识别音量加/减/静音键
      -> bootVideoSetVolume(UP/DOWN/MUTE)
          -> 修改 mVol / mMute
          -> MediaPlayer::setVolume()
          -> 持久化 persist.sys.bootvideo

bootVideo()
  -> bootVideoVolumeUI()
      -> 加载 bootvideo.zip
      -> 根据当前 mVol 选择帧
      -> 绘制音量 UI
      -> 4 秒无操作自动隐藏
```

从时序上看，音量输入线程和音量 UI 绘制线程是并行配合的：

1. 输入线程负责改状态。
2. UI 循环负责感知状态变化并刷新画面。

### 35.9 常见排查建议

如果后续遇到“开机动画不显示、只播黑屏、视频无声、时钟不显示、音量键无效”等问题，可以按下面顺序查：

#### 1. 动画完全不显示

优先检查：

1. `debug.sf.nobootanimation`
2. `ro.boot.quiescent`
3. `persist.vendor.media.bootvideo`
4. `persist.vendor.media.bootvideo.tsplayer`
5. `SurfaceFlinger` 是否已正常起来

#### 2. zip 动画资源未生效

优先检查：

1. 路径优先级是否被更高分区覆盖
2. zip 是否采用 `store` 而非压缩模式
3. `desc.txt` 是否格式正确
4. PNG 帧命名和 zip 中顺序是否正确

#### 3. 开机音频不播放

优先检查：

1. part 目录下是否存在 `audio.wav`
2. `persist.sys.bootanim.play_sound`
3. `sys.boot_completed`
4. `sys.powerctl`
5. `ro.boot.bootreason` 是否命中异常重启黑名单

#### 4. 时钟不显示

优先检查：

1. part 是否配置了时钟坐标
2. `persist.sys.bootanim.clock.enabled`
3. `/data/bootanim/time/time_is_accurate`
4. `/data/bootanim/time/last_time_change`

#### 5. boot video 不播放

优先检查：

1. `persist.vendor.media.bootvideo` 模式值
2. `/data/bootvideo` 或 `/vendor/etc/bootvideo` 是否存在
3. `media.player` 服务是否启动
4. `media.omx.display_mode` 相关模式配置

#### 6. 开机视频音量键无效

优先检查：

1. `InputReaderThread` 是否启动
2. `/dev/input` 下目标设备是否被成功打开
3. 上报按键是否为 `KEY_VOLUMEUP / KEY_VOLUMEDOWN / KEY_MUTE`
4. `persist.sys.bootvideo` 是否有更新

## 37. `desc.txt` 配置示例大全

这一节专门整理 `bootanimation.zip` 中 `desc.txt` 的常见写法，尽量覆盖实际项目中最常用的配置场景。

### 37.1 `desc.txt` 基本规则

`desc.txt` 的结构分为三部分：

1. 第一行：整体动画参数
2. 第二行：可选的 `dynamic_colors` 配置
3. 后续多行：每个 `part` 的播放规则

基本格式如下：

```text
WIDTH HEIGHT FPS [PROGRESS]
[dynamic_colors PATH #RGBHEX0 #RGBHEX1 #RGBHEX2 #RGBHEX3 [START END]]
TYPE COUNT PAUSE PATH [FADE [#RRGGBB [CLOCK1 [CLOCK2]]]]
TYPE COUNT PAUSE PATH [FADE [#RRGGBB [CLOCK1 [CLOCK2]]]]
...
```

### 37.2 第一行字段说明

第一行格式：

```text
WIDTH HEIGHT FPS [PROGRESS]
```

示例：

```text
1920 1080 30
```

或者：

```text
1920 1080 30 1
```

字段含义：

1. `WIDTH`：动画设计宽度
2. `HEIGHT`：动画设计高度
3. `FPS`：动画帧率
4. `PROGRESS`：可选，`1` 表示允许在最后一个 part 显示开机进度百分比

说明：

1. `PROGRESS` 不写时，默认不显示进度。
2. `PROGRESS` 写了也不是所有 part 都显示，只在最后一个 part 上显示。

### 37.3 part 行字段说明

part 基本格式：

```text
TYPE COUNT PAUSE PATH [FADE [#RRGGBB [CLOCK1 [CLOCK2]]]]
```

字段含义：

1. `TYPE`
   - `p`：普通 part，可被中断
   - `c`：完整播放 part，收到退出信号也要播完
   - `f`：可被中断，但退出时支持淡出
2. `COUNT`
   - 正整数：播放指定次数
   - `0`：无限循环，直到系统发出退出信号
3. `PAUSE`
   - part 播放结束后停顿多少帧
4. `PATH`
   - 对应 zip 中的目录名，如 `part0`
5. `FADE`
   - 仅 `f` 类型有效，表示淡出帧数
6. `#RRGGBB`
   - 可选，背景色
7. `CLOCK1 CLOCK2`
   - 可选，时钟位置

### 37.4 时钟坐标规则

时钟位置支持：

1. 正整数
2. 负整数
3. `c`

含义如下：

1. `c`：居中
2. 正数：从左边或底边开始偏移
3. 负数：从右边或顶边反向偏移

常见写法：

```text
c -24
```

表示：

1. 水平居中
2. 距离顶部 24 像素

```text
16 c
```

表示：

1. 距离左边 16 像素
2. 垂直居中

```text
-32 32
```

表示：

1. 距离右边 32 像素
2. 距离底边 32 像素

### 37.5 特殊行 `$SYSTEM`

`desc.txt` 里还支持：

```text
$SYSTEM
```

含义是：

直接插入 `/system/media/bootanimation.zip` 作为一个嵌套动画段进行播放。

适合场景：

1. 前面先播厂商 logo
2. 后面接系统默认动画

## 39. 循环等待类示例

### 39.1 先播一次 logo，再无限循环等待开机完成

这是最常见的手机/平板开机动画模型。

示例：

```text
1920 1080 30
p 1 0 part0
p 0 0 part1
```

说明：

1. `part0` 播放一次，通常放品牌展示
2. `part1` 无限循环，直到系统设置 `service.bootanim.exit=1`

业务含义：

1. 系统启动快时，循环 part 可能播很少几次
2. 系统启动慢时，循环 part 会一直兜底等待

### 39.2 循环段结束后带停顿

示例：

```text
1920 1080 24
p 1 0 part0
p 0 6 part1
```

说明：

1. `part1` 每播完一轮后，额外停 `6` 帧
2. 适合做呼吸灯、波纹、旋转圈等不想太快的等待动画

## 40. 必须完整播放类示例

### 40.1 退出信号到来后仍然必须播完当前段

适合场景：

1. 最后一段是品牌完成态
2. 希望即使系统 boot 完成，也把收尾动作完整放完

示例：

```text
1920 1080 30
p 1 0 part0
p 0 0 part1
c 1 0 part2
```

说明：

1. `part0` 播一次
2. `part1` 无限循环等待
3. 收到退出信号后，`part1` 可以停止
4. 但 `part2` 若轮到播放，就必须完整播完一次

业务价值：

1. 能做比较完整的“收尾动画”
2. 避免动画在最关键一帧戛然而止

### 40.2 多段必须完整播放

示例：

```text
1920 1080 30
p 1 0 part0
c 1 0 part1
c 1 0 part2
```

说明：

1. 后两段都属于必须完整播放
2. 即使退出信号来了，也会坚持播完

注意：

这种写法视觉上更稳定，但可能延长进入系统桌面的时间感知。

## 41. 淡出类示例

### 41.1 无限循环段在退出时淡出

适合场景：

1. 等待阶段动画不想突然消失
2. 希望系统进入桌面时更柔和

示例：

```text
1920 1080 30
p 1 0 part0
f 0 0 part1 15
```

说明：

1. `part0` 播一次
2. `part1` 无限循环
3. 收到退出信号后，不会立刻切断，而是在 `15` 帧内淡出

### 41.2 带背景色的淡出段

示例：

```text
1920 1080 30
p 1 0 part0

```

说明：

1. `part1` 使用黑色背景
2. 退出时在 `20` 帧内淡出

### 41.3 淡出段后再接一个完整收尾段

示例：

```text
1920 1080 30
p 1 0 logo
f 0 0 loop 12
c 1 0 finish
```

说明：

1. `logo` 播一次
2. `loop` 无限循环等待
3. 收到退出信号时，`loop` 先做 12 帧淡出
4. 然后 `finish` 再完整播一遍作为收尾

这是一种实际项目里很常见的优雅退出方案。

## 45. 动态换色类示例

### 45.1 最基础的动态换色

动态换色配置必须写在第二行。

示例：

```text
1920 1080 30
dynamic_colors part1 #FF0000 #00FF00 #0000FF #FFFFFF
p 1 0 part0
p 0 0 part1
```

说明：

1. `part1` 是动态换色段
2. 起始四种颜色分别对应 RGBA 四个 mask 通道
3. 终点颜色从以下属性读取：
   - `persist.bootanim.color1`
   - `persist.bootanim.color2`
   - `persist.bootanim.color3`
   - `persist.bootanim.color4`

如果这些属性没配，终点颜色默认等于起始颜色，也就是不会真正发生过渡。

### 45.2 带过渡区间的动态换色

当前源码解析时还支持在动态换色行末尾追加起止帧。

示例：

```text
1920 1080 30
dynamic_colors part1 #FF0000 #00FF00 #0000FF #FFFFFF 10 50
p 1 0 part0
p 0 0 part1
```

说明：

1. 在 `part1` 的第 10 帧到第 50 帧之间完成颜色过渡
2. 10 帧之前更接近起始颜色
3. 50 帧之后更接近终点颜色

### 45.3 动态换色前后分段示例

示例：

```text
1920 1080 30
dynamic_colors color_part #112233 #445566 #778899 #FFFFFF 0 30
p 1 0 intro
p 0 0 color_part
c 1 0 outro
```

说明：

1. `intro` 会按起始颜色效果渲染
2. `color_part` 发生颜色渐变
3. `outro` 会按结束颜色效果渲染

这个机制非常适合做主题色从品牌色过渡到系统色的启动动画。

### 45.4 动态换色素材要求

做这种动画时要注意：

1. PNG 不是普通彩色图思路，而是 mask 图思路
2. R、G、B、A 四个通道分别代表四种颜色区域
3. 如果四个通道都较高，shader 会把该区域渲染成偏白效果

所以设计素材时要和普通 PNG 动画区分开。

## 49. 配置注意事项

### 49.1 zip 必须使用 store 模式

源码要求 zip entry 是 `stored`，不是 `deflate` 压缩。

推荐打包命令：

```bash
zip -0qry -i \*.txt \*.png \*.wav @ ../bootanimation.zip *.txt part*
```

其中关键是：

```bash
-0
```

表示不压缩。

### 49.2 帧文件命名要有序

建议统一使用：

```text
00000.png
00001.png
00002.png
...
```

避免 zip 内部顺序与预期播放顺序不一致。

### 49.3 `trim.txt` 要和帧顺序一一对应

如果某个 part 使用了 `trim.txt`，则：

1. `trim.txt` 每一行必须对应一帧
2. 行数和帧数量至少要能覆盖实际需要的帧

否则定位会出错或回退默认尺寸。

### 49.4 透明图建议配合背景色验证

很多素材带透明通道时，实际显示效果会受背景色影响很大。

建议：

1. 有透明元素的 part 明确写背景色
2. 尤其是黑底或白底主题时避免设计误差

### 49.5 进度只显示在最后一个 part

这点非常容易误解。

即使写了：

```text
1920 1080 30 1
```

也不是所有 part 都显示进度，而是只在最后一个 part 上显示。

### 49.6 时钟显示不只依赖 `desc.txt`

即使写了时钟位置，也要同时满足：

1. 开关属性打开
2. 系统时间准确
3. 字体资源可用

所以时钟不显示时，不一定是 `desc.txt` 写错了。

### 49.7 `f 0 0 part1 0` 基本等价普通 `p`

因为淡出帧数为 `0` 时，不会形成真正的淡出效果。

所以这种配置一般没有实际意义。

## 50. 推荐起步模板

如果要从零开始做一个比较稳妥的开机动画，推荐先用下面这个模板：

```text
1920 1080 30
p 1 0 logo #000000
f 0 0 loop 12 #000000
c 1 0 finish #000000
```

推荐原因：

1. `logo` 负责品牌首屏
2. `loop` 负责兜底等待系统启动
3. `finish` 负责优雅收尾
4. 整体逻辑简单，调试成本低
5. 后续很容易继续加进度、时钟、动态换色

如果需要进度版本，可以改成：

```text
1920 1080 30 1
p 1 0 logo #000000
f 0 0 loop 12 #000000
```

如果需要时钟版本，可以改成：

```text
1920 1080 24
f 0 0 watchface 12 #000000 c -24
```

## 51. `desc.txt` 示例大全小结

可以把 `desc.txt` 的设计思路总结成一句话：

第一行决定“整套动画怎么跑”，每个 part 决定“每一段怎么播”，而 zip 目录本身决定“具体播哪些帧”。

实际配置时，最常见的三种模板分别是：

1. `单段播放`
2. `首段展示 + 无限循环等待`
3. `首段展示 + 循环等待 + 淡出/收尾`

如果项目需要更强视觉表现，再在这个基础上逐步叠加：

1. 背景色
2. 时钟
3. 进度
4. 音频
5. 动态换色
6. `$SYSTEM` 嵌套系统动画
